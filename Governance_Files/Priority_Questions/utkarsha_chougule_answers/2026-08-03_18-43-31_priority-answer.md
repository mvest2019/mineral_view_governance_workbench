Question:
Do the stored Previous/Current Page URLs capture owner names, lease IDs, or other PII in the path or query string?

Answer:
pageurl and previouspageurl are persisted verbatim. No masking, truncation, hashing, or query-string stripping is applied at any point — the backend's documented pipeline (validate → clamp → resolve IP → detect mobile → filter bots → upsert) does not modify the URL. Whether the query string is transmitted at all depends on the client capture line in user-tracking.tsx; [pending / confirmed as X]. Production scan of N rows shows [results of the query above].

Note that path-only storage does not resolve this: lease, well, and owner-scoped routes carry identifiers in the path itself, and RRC lease and API numbers are re-linkable to named owners via public records. Combined with the stable visitorid, full ipaddress, and userid, the table currently constitutes a per-person browsing history.

Raising as a finding with proposed remediation: (1) client sends route pattern rather than resolved URL, e.g. /lease/[id], with identifiers dropped or hashed; (2) query strings stripped to an allow-list at capture and again server-side as defence in depth; (3) never persist free-text search terms; (4) decide explicitly whether ipaddress is needed at all, and note that current values are Cloudflare edge IPs, not client IPs. Requires Nikhil for implementation scope and Ryan for the retention/collection decision on existing rows.

The existing rows are the part people forget. If the scan comes back positive, remediation isn't only forward-looking — you'll need a decision on purging or rewriting what's already stored.
