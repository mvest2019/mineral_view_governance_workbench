# Priority Question Answer

Question:
Does the registry-based fix bypass the CMS's tag-stripping sanitization, and did anyone review that as an XSS risk?

Answer:
Properly implemented, the registry approach does not bypass the sanitizer — it works within it, and that's the point of the design: CMS content still passes through the tag blocklist untouched (no <script>/<style> ever enters the content field), and the only executable code is dev-authored, dev-deployed components that the registry mounts onto inert placeholder markup — so the XSS trust boundary ("CMS authors cannot inject code") is preserved, unlike the rejected raw-injection route. What it bypasses is only the styling limitation, and even that goes through the dev handoff (Rohit's updated CSS is deployed by devs into global assets, never inline). No formal security review is on record, though — the XSS rationale was explicitly considered in the design discussion (the sanitizer's purpose was acknowledged and respected), but the fix should still get a one-time dev/security sign-off confirming two invariants: the registry only mounts a fixed allowlist of components, and no CMS-supplied string is ever evaluated or set as raw HTML by those components.
