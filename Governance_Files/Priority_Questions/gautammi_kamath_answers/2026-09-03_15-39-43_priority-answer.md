# Priority Question Answer

Question:
Do the new attribution events capture any personal or payment data, and are they covered by the privacy policy and consent?

Answer:
The events carry no card data and are specified carefully, but every one of them carries a direct user identifier, one is already live and already breaching its own spec, and the consent gate the specification depends on does not exist — four trackers run unconsented on the live site today. The privacy policy is three years old, names no analytics processor, and names the wrong payment processor. Verified against 10-attribution-instrumentation-spec.md, 15-funnel-event-definitions.md, live Production, and the live site on 1 Sep 2026.

The specification already sets the gate. Doc 10 §7 is titled "Consent & privacy requirements (gate — must clear before launch)" and closes: "This section is a launch gate: no click-ID storage, enhanced conversions, or offline uploads go live until legal/privacy sign-off is obtained." It requires Google Consent Mode v2 driven "from the consent tool", names CCPA and the Texas Data Privacy and Security Act, requires honouring Global Privacy Control, and requires that we "update the privacy notice to disclose click-ID and hashed-PII collection and the purposes." §0 principle 3 is "Consent first." The field table defines a consent_state field whose source is "consent tool". There is no consent tool. So the honest answer to this question is not that consent was overlooked — it is that the gate was written, and the site is already on the wrong side of it.

What each event carries.

Event	Identifiers	Money fields	Error fields	Card data
pricing_view	user_id or anonymous_id, session_id	price, currency	none	none
checkout_start	user_id, anonymous_id, session_id, checkout_session_id	price, currency	none	none — provider tokenizes
payment_success	user_id (required), session_id, transaction_id	amount_collected, currency, provider_status = settled	none	none
payment_failed	user_id, session_id, transaction_attempt_id	amount_attempted, currency	failure_reason_category (categorized)	none
checkout_error	user_id or anonymous_id, session_id	optional plan context	journey_stage, error_category, error_code, endpoint, http_status	none

The shared conventions are correct and strict: never raw card number, CVV or bank details in any payload; email and phone only as normalized SHA-256 hashes, only for enhanced conversions, only with consent; checkout_error carries "categorized codes, not raw stack traces." No event carries a name, address, phone or cleartext email.

One line in the spec should not reach counsel unchallenged. pricing_view is annotated "no PII beyond identifiers." All five events carry user_id, and payment_success requires it because "a settled payment is always a known user." A member ID joined to a known account is personal data under TDPSA Ch. 541 and under CCPA/CPRA — pseudonymous, not anonymous. These events tie identified individuals to purchase behaviour and amounts. That is their purpose, and the annotation understates it.

Where the data lands — three destinations, and the primary one is undefined.

1. The analytics events store: not specified. Every event's destination field reads [CONFIRM destination — events table / warehouse]. Governance asks where the data lands, and the spec does not yet say. That gap has to be closed by dev, with retention and access controls named alongside it.

2. GA4 and Google Ads via GTM — verified PII-free. Rohit's purchase handoff (Q-AI-0688, 27 Aug) gives the complete field list: transaction_id, value, currency, and one item carrying item_id (plan slug), item_name, item_category, item_variant, price, quantity. Dev is explicitly instructed not to use the member ID as transaction_id, and the container publishes only after GTM Preview and GA4 DebugView verification.

3. Postgres — live, and in the wrong shape. checkoutpageinfo_api_track is the de facto checkout_error implementation running today. It stores member_id, ip_address, user_agent, full request_payload and response_payload JSON, error_message, and error_stack — 19 rows currently hold Node stack traces with absolute server paths (…\PresentationSiteAPI\api\v1.0\Services\subscriptionService.js:2409). Doc 15 §5 forbids exactly this: "no raw stack traces, no raw request/response bodies, no PII or payment data in the analytics payload — categorized codes only; full traces stay in access-controlled server logs." So yes — one of these events already captures personal data (IP, user agent) and server internals, in an analytics table rather than in secured logs.

Is the tracking disclosed? Partially, and inadequately. The live policy is "Last Updated: June 1, 2023." It discloses the categories — IP address, browser characteristics, device ID, operating system, referring URLs, URLs visited, traffic data, location, cookies for unique-visitor identification, and "web beacons or clear gifs to track user online movements and the effectiveness of its marketing campaigns" — and it discloses collecting payment and billing information. But:

It names no analytics or advertising processor — no Google Analytics, Google Ads, Google Tag Manager or Microsoft Clarity. There is no subprocessor list, which is one of DEC-61's four gaps, owned by Counsel and unrouted.
It names the wrong payment stack: "a verified Cybersource & Payeezy e-Commerce payment gateway merchant" and "processed securely by Authorize.net." The live processor is Braintree, confirmed by Rohit on 27 Aug and evidenced by braintree_transaction_id on every completed checkout.
Its only state-law provision is California "Shine the Light." There is no CCPA/CPRA notice and no TDPSA notice, for a Texas LLC whose policy is governed by Texas law — while doc 10 §7 names TDPSA as directly applicable.
It says nothing about click IDs or hashed PII, which §7 requires before enhanced conversions can run.

Is it consented? No — and the evidence is unambiguous. On www.mineralview.com, with no user interaction:

GA4 G-NWJG8V9E90, Google Ads AW-17628960056, GTM GTM-PHSLNT33 and Microsoft Clarity w49ek0p8jb all load on first page view.
Cookies _ga, _ga_NWJG8V9E90, _gcl_au, _clck, _clsk are written immediately.
A googleads.g.doubleclick.net/pagead/viewthroughconversion/17628960056/ request fires, carrying npa=0 — personalised advertising not restricted.
No consent platform exists. Tested for OneTrust, Cookiebot, CookieYes, Osano, Klaro, usercentrics, Didomi, Termly, TrustArc, Iubenda and IAB TCF __tcfapi — all absent. No consent-like element appears anywhere in the DOM against a wide keyword set including "got it", "I agree", "allow all", "reject" and "manage preferences". The dataLayer contains only gtm.js, gtm.dom and gtm.load — no consent event.
Google Consent Mode reports all four signals — ad_storage, ad_personalization, ad_user_data, analytics_storage — as implicit: true, meaning no default was declared and no update was ever called. Consent Mode is present in name only, and everything is granted by implication.

Doc 10 §7 requires honouring GPC; doc 19 §11 records that this is mandatory in California under 11 CCR §7025 and available under TDPSA §541.055(e) since 1 Jan 2025. With no CMP, neither is honoured.

Which makes one specified condition currently unsatisfiable. Hashed email and phone are permitted "only for enhanced conversions with consent." There is no consent capture, so enhanced conversions cannot lawfully be enabled as designed, and §7's launch gate cannot clear.

And the documents that would fix the disclosure are placeholders. node tools/check-legal.mjs --publish exits 1 on four documents with five placeholders, including PRIV and COOKIE. DEC-61 — DMCA agent, subprocessor list, AI provider terms, cookie register — is owned by Counsel and cannot be routed, because D-3 (who receives legal questions) has never been decided. That is the same blocker as Q-AI-0003.

A live exposure on a public page that should be closed this week. /pricing is public and carries Clarity, GA4, Google Ads and GTM with zero consent elements — and the page contains an <input type="email"> with no data-clarity-mask attribute. Clarity is a session-recording tool. Whether that field's contents are captured depends on the project's masking mode, a Clarity dashboard setting I cannot read from the page. An unmasked-by-attribute email input sits on a session-recorded, unconsented public page today. Confirm the masking mode, and confirm separately whether Clarity and the ad tags load on the authenticated /payment route — I checked public pages only.

Recommended disposition.

Fix the live spec violation. Stop writing error_stack, raw payloads, IP and user agent into checkoutpageinfo_api_track; move traces to access-controlled logs and keep a redacted reference id, per doc 15 §5. No counsel needed.
Verify Clarity masking on /pricing and every checkout route, with evidence.
Resolve [CONFIRM destination] — name the events store, its retention period and its access controls.
Install a CMP. Consent Mode is wired with four signals and nothing drives them; this is the single change that turns implicit: true into a defensible position and unblocks §7.
Rewrite the privacy policy. Three years stale, wrong payment processor, no analytics processors, no TDPSA notice, no click-ID or hashed-PII disclosure. D-020 makes drafting ours — "we draft first, counsel reviews later" — so this needs no approval to start.
Amend the spec line from "no PII beyond identifiers" to state that these events process pseudonymous personal data linked to identified members, so counsel scopes the correct question.

The finding underneath. This instrumentation design is the most disciplined compliance work in the package: it bans card data, categorizes errors, hashes contact fields, gates attribution on consent, names the applicable statutes, and defines its own launch gate. It was specified against an environment with no consent tool, a 2023 privacy policy naming the wrong payment processor, placeholder PRIV and COOKIE documents, four trackers already running with consent implicit-granted, and a session recorder on a public page with an unmasked email field. The new events are not the risk. The gate they were written to clear is already breached by what is live.
